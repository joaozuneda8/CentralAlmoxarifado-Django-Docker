# Implantação em Docker — plano de implementação

> **Situação:** executado. As caixas abaixo não foram marcadas durante a execução; o que vale
> hoje está no código e no `CLAUDE.md`.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implantar o sistema só por Docker Compose (banco, web, agendador), no lugar do NSSM,
do Agendador do Windows e dos `.bat`.

**Architecture:** Uma imagem (Python 3.13 + `.venv` do uv + Chromium do Playwright +
`mariadb-client` + supercronic, estáticos coletados no build, usuário `almox`) serve aos
serviços `web` (waitress) e `agendador` (supercronic com `deploy/crontab`); o `banco` é o
MariaDB 11.4 sem porta publicada. O Apache existente continua com o HTTPS e encaminha para
`${PORTA_PUBLICADA}`.

**Tech Stack:** Docker Engine + compose v2, `python:3.13-slim-bookworm`, uv, Playwright,
MariaDB 11.4, supercronic, waitress, bash.

**Spec:** `docs/superpowers/specs/2026-10-15-docker-design.md`

## Global Constraints

- Textos, nomes, comentários e commits em português (pt-BR), como o resto do projeto.
- Python da série 3.13 (`requires-python = ">=3.13,<3.14"`); dependências por `uv sync --frozen --no-dev`.
- Imagens e binários com versão fixada: `python:3.13-slim-bookworm`, `mariadb:11.4`, o `uv`
  por tag exata de `ghcr.io/astral-sh/uv` (a versão do `uv --version` local), o supercronic por
  versão e SHA-1 do release no GitHub.
- Fuso `America/Sao_Paulo` na imagem (`TZ`, com `tzdata` instalado).
- O código e o `.venv` na imagem pertencem ao root; o processo roda como `almox` (UID 1000) e
  só escreve em `/dados`.
- O banco nunca tem porta publicada; o `web` publica `${PORTA_PUBLICADA:-127.0.0.1:8010}:8010`.
- O compose força `DB_HOST=banco`, `DB_PORT=3306`, `SCPI_HEADLESS=1`, `MYSQLDUMP=mariadb-dump`,
  `LOG_DIR=/dados/logs`, `BACKUP_DIR=/dados/backups`, `SCPI_PERFIL_DIR=/dados/perfil`.
- `deploy/*.sh` e `deploy/crontab` com fim de linha LF (`.gitattributes`) e bit de execução no git.
- O `settings.py` não muda.
- Testes rodam localmente contra MySQL/MariaDB (`uv run pytest`); nenhum teste chama `docker`.

## Review Focus

- `PREFIXO_URL` vazio (site na raiz): o compose precisa passar `--url-prefix=` vazio sem
  quebrar o waitress e o `MARIADB_DATABASE` precisa do padrão `almoxarifado` quando `DB_NAME`
  está vazio. Testes na Task 3.
- Senha com `$` no `.env`: o compose interpola `$` no `.env` e a senha mudaria em silêncio. O
  `.env.example` avisa (aspas simples ou sem `$`). Teste na Task 3.
- `atualizar.sh` rodado com o `web` parado (primeira instalação, depois de um `down`): o
  `robos_em_andamento` por `exec` falharia sempre. Usa `docker compose run --rm` (sobe o banco
  se preciso). Teste na Task 4.
- Horário do agendador fora do fuso: sem `TZ` e `tzdata`, o supercronic roda em UTC e o
  estoque cai das 04:00 às 14:00. Teste na Task 3 (Dockerfile) e Task 2 (crontab).
- Scripts com CRLF vindos de um checkout no Windows: `bash` recusa `set -eu\r`. Teste dos bytes
  nas Tasks 2 e 4.
